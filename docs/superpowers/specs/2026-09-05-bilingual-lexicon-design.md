# 대역어 사전 생성 설계

**날짜:** 2026-09-05
**상태:** 설계 완료, 엔진 선택 대기
**선행 문서:** `docs/superpowers/specs/2026-09-02-word-explanation-datasource-design.md`

---

## 1. 배경

`2026-09-02` 설계로 자막의 단어와 구동사에 한국어 뜻을 붙였다. 무료 위키 덤프
두 종을 병합해 만든 정적 사전을 Firebase Hosting에서 받아 쓴다. 그 설계는
한국어 커버리지의 한계를 처음부터 알고 받아들였지만, **그 한계의 크기를 잘못
알고 있었다.**

### 1.1 정정 — 실제 커버리지는 훨씬 낮다

선행 설계 §2.2는 "일반 단어 30/30(100%)"이라는 표본으로 단일 단어의 한국어
커버리지가 사실상 완전하다고 적었다. 그 30개는 손으로 고른 것이라 편향돼
있었다. OpenSubtitles 자막 빈도 목록(hermitdave/FrequencyWords, 영어 5만 단어)을
기준으로 실제 사전을 조회해 다시 측정한 결과다.

| 자막 빈도 구간 | ko 보유 | ko 없음 | 보유율 |
|---|---|---|---|
| 상위 1,000 | 797 | 194 | 80% |
| 상위 5,000 | 3,240 | 1,731 | 65% |
| 상위 10,000 | 5,267 | 4,635 | **53%** |
| 상위 20,000 | 7,687 | 11,840 | 39% |
| 상위 50,000 | 10,687 | 34,774 | 24% |

**자막에 가장 흔한 1만 단어 중 절반이 한국어 뜻 없이 영영 정의로 폴백된다.**
선행 문서 §14.2의 "흔한 단어 기준 커버리지는 §2.2 실측이 맞다"는 서술은 틀렸다.

구동사는 더 나쁘다. 품사로 거른 `mwe-index` 72,069개 중 **71,644개(99.4%)에
한국어 뜻이 없다.** 선행 설계가 측정한 "구동사 52%"는 흔한 구동사 60개 표본의
값이고, 인덱스 전체로는 사실상 전부가 비어 있다.

### 1.2 무료 소스로는 더 못 채운다

en.wiktionary의 한국어 번역과 ko.wiktionary의 영어 표제어를 이미 합집합으로
쓰고 있다. 이 둘이 우리가 가진 전부이고, 연어(`heavy rain`, `make a decision`)는
어느 쪽에도 표제어가 없다. 채우려면 **없는 대역어를 만들어 내야 한다.**

## 2. Language Reactor 조사 (2026-09-05)

같은 문제를 푼 제품이 어떻게 하는지 API를 직접 호출해 확인했다.

**핵심 발견 — 무료 사전 덤프를 쓰지 않는다.** 우리 사전이 한국어를 못 주는
표현을 넣으면 전부 답한다.

| 표현 | 우리 | Language Reactor |
|---|---|---|
| put up with | 없음 | 참다, 견디다, 인내하다, 감수하다 |
| find out | 없음 | 알아내다, 밝혀내다, 찾아내다 |
| deal with | 없음 | 처리하다, 다루다, 대처하다 |
| run into | 없음 | 우연히 만나다, 마주치다, 부딪히다 |
| heavy rain | **표제어 없음** | 폭우, 호우, 장대비, 집중호우 |
| make a decision | **표제어 없음** | 결정하다, 정하다, 결심하다 |

마지막 두 줄이 결정적이다. `heavy rain`은 어느 위키사전에도 표제어가 없는데
LR은 답한다. 위키 파생이 아니라 **자체 구축한 이중언어 사전**이라는 뜻이다.

**API 형태** (`api-cdn-plus.dioco.io`):

```
base_dict_getFullDict_8?form=started&lemma=start&sl=en&tl=ko&pos=VERB
```

요청에 이미 `lemma`와 `pos`가 들어 있다 — 자막 전체에 품사 태깅과 표제어
추출을 미리 돌려 둔다는 뜻이다(`pos=VERB`는 Universal Dependencies 태그셋).

**응답 형태:**

```json
{ "word": "start", "posGroups": [
    { "pos": "verb", "translations": ["시작하다","개시하다","착수하다","시작되다"] },
    { "pos": "noun", "translations": ["시작","개시","착수"] } ] }
```

정의문도 발음기호도 출처 표기도 없다. **품사별 대역어 목록뿐이다.**

**그 밖에 확인된 것**
- 예문은 Tatoeba(CC-BY, 기여자 이름까지 표기)
- 문맥 설명("이 문장에서 '시작하다'라는 뜻")은 LLM (`base_dict_llmDict`)
- 외부 사전은 전부 **링크아웃**이다: Reverso, Cambridge, Naver, Glosbe,
  **ko.wiktionary**, bab.la. 우리가 사전 본체로 쓰는 소스를 그들은 "더 찾아보기"
  링크로만 쓴다
- 인프라는 Firebase Auth + Cloud Functions + 자체 CDN — 우리와 같은 스택

**시사점:** 우리 구조(자막 선처리 → 배치 조회 → 형태 인지 매칭)는 LR과 같은
뼈대다. 격차는 알고리즘이 아니라 **데이터**에서 온다.

## 3. 현재 구조 (as-is)

### 3.1 외부 의존

확장이 호출하는 외부 도메인은 이게 전부다.

| 용도 | 대상 | 성격 |
|---|---|---|
| 로그인 | `identitytoolkit.googleapis.com` | Firebase Auth |
| 토큰 갱신 | `securetoken.googleapis.com` | Firebase |
| 학습 데이터 동기화 | `firestore.googleapis.com` | Firestore REST |
| **사전 조회** | `language-helper-d1de6.web.app` | **정적 파일** |
| 자막 | 플랫폼 자체 자막 트랙 | — |

**번역 API도 LLM API도 쓰지 않는다.** 사전은 API가 아니라 빌드해서 올려 둔
JSON이다. `cloud/config.js`의 `apiKey`는 Firebase 프로젝트 식별자로, 과금과
무관하며 접근 제어는 Firestore 보안 규칙이 한다.

### 3.2 사전 파이프라인

```
[빌드 · 개발 PC · 수동]
  kaikki English JSONL (3.2GB) ─┐
                                ├─→ tools/build-dictionary.js ─→ dist/dict/
  kowiktionary XML.bz2 (47MB)  ─┘         (버킷 11,409개 + 인덱스 3종)
[배포]  firebase deploy --only hosting
[런타임] service worker: lexicon/lookup.js → IndexedDB 캐시 → Hosting fetch
```

레코드는 `{ pos: [], ko: [], en: [], ipa, mwe }`이고, `ko`가 비어 있을 때만
`en`으로 폴백한다(선행 설계 §5).

## 4. 목표와 범위

**목표:** `ko`가 비어 있는 표제어에 대역어를 만들어 채운다. 런타임 구조와
배포 방식은 그대로 둔다.

**범위 (확정):** 106,418개
- 품사로 거른 `mwe-index` 중 `ko` 없는 것 **71,644개**
- 자막 빈도 상위 5만 단어 중 `ko` 없는 것 **34,774개**

상위 5만 밖의 단일 단어(약 98만 개)는 제외한다. 자막에 사실상 나오지 않으며,
비용은 10배로 뛰고 얻는 게 없다. 영영 정의 폴백을 그대로 둔다.

**제외:**
- 런타임 LLM 호출 — 문맥 기반 의미 선택은 여전히 하지 않는다
- 기존 `ko`(위키 출처)를 대역어로 덮어쓰기 — 사람이 쓴 뜻이 우선이다
- 발음기호·예문 추가 — 별도 사안
- 앱(Flutter) 변경

## 5. 접근

빌드 파이프라인에 **한 단계**를 끼운다. 런타임 코드, 배포 방식, 버킷 구조,
조회 계층은 손대지 않는다.

```
kaikki + kowiktionary ─→ 병합 (현행) ─→ ko 없는 표제어 추출
                                              ↓
                                    대역어 생성 (신규, 1회)
                                              ↓
                                    lexicon/gloss-cache.json
                                              ↓
                          병합 (현행) + 캐시 주입 ─→ dist/dict/
```

**캐시 파일이 핵심이다.** 생성 결과를 `lexicon/gloss-cache.json`에 저장하고
**저장소에 커밋한다.** 이유:

1. 사전을 재빌드해도 이미 만든 대역어는 다시 만들지 않는다 — 비용이 1회로 끝난다
2. 결과가 코드 리뷰와 git 이력에 남는다. 이상한 대역어가 나오면 추적·수정 가능하다
3. 다른 사람이 덤프만 받으면 API 키 없이 같은 사전을 빌드할 수 있다

캐시 키는 `표제어 + 품사`이고 값은 대역어 배열이다. 위키 덤프가 갱신돼도
표제어가 그대로면 캐시가 유효하다. 항목당 약 60바이트로 잡으면 106,418개에
**약 6MB**다. 저장소에 두기에 큰 편이지만, 이 파일이 곧 지출한 비용의 결과물이므로
잃지 않는 쪽이 맞다. `dist/`처럼 재생성 가능한 산출물과 성격이 다르다.

## 6. 엔진 — 비용과 선택

번역 대상 문자수를 실제로 세어 계산했다.

| 항목 | 개수 | 표제어만 | 표제어+영영 정의 |
|---|---|---|---|
| 구동사·관용구 | 71,644 | 1,134,231자 | 5,351,053자 |
| 단일 단어 상위 5만 | 34,774 | 248,000자 | 3,062,500자 |
| **합계** | **106,418** | **1,382,231자** | **8,413,553자** |

**표제어만 넘기면 안 된다.** `look up`만 던지면 "위를 보다"가 나온다. Wiktionary
영영 정의를 문맥으로 함께 넘겨야 모호성이 사라진다. 아래 비용은 정의 포함 기준이다.

### 6.1 후보 A — Google Cloud Translation

$20/100만 자, 매월 50만 자 무료 (반복 크레딧).

- 표제어+정의 8,413,553자 → **$168** (약 23만원)
- 표제어만 1,382,231자 → **$28** (약 3.8만원, 모호성 위험 감수 시)

**문제는 출력 형태다.** 번역기는 "To tolerate; to endure"를 "참는 것; 견디는 것"
같은 **문장**으로 돌려준다. 우리가 필요한 건 `["참다","견디다","인내하다"]`라는
**대역어 목록**이다. 문장에서 목록을 뽑는 후처리가 한 단계 더 필요하고, 그
후처리가 또 다른 오류원이 된다.

### 6.2 후보 B — Claude Haiku 4.5 + Batch API (추천)

Haiku 4.5는 입력 $1 / 출력 $5 (100만 토큰당), Batch API는 50% 할인.

추정 (영어 3.6자/토큰, 항목당 출력 약 80토큰 가정):
- 입력 8.41M자 ≈ 2.5M 토큰 → $2.50 → 배치 **$1.25**
- 출력 106,418 × 80토큰 ≈ 8.5M 토큰 → $42.6 → 배치 **$21.3**
- **합계 약 $22.6** (약 3만원)

**번역 API보다 싸면서 원하는 모양이 바로 나온다.** 프롬프트로 품사별 대역어
목록을 JSON으로 요구할 수 있고, 이는 Language Reactor의 `posGroups` 구조와 같다.
Structured outputs(`output_config.format`)로 스키마를 강제하면 파싱 실패도 없다.

### 6.3 비교

| | Google 번역 | Claude Haiku + Batch |
|---|---|---|
| 비용 | $168 (정의 포함) | **약 $23** |
| 출력 | 번역된 문장 | **품사별 대역어 JSON** |
| 후처리 | 목록 추출 필요 | 불필요 |
| 모호성 | 정의를 함께 넘겨 완화 | 정의를 문맥으로 지시 가능 |
| 품질 검증 | 필요 | 필요 |

**추천은 B다.** 다만 이 판단은 추정 토큰 수에 기대고 있으므로, 확정 전에
§10의 표본 검증을 먼저 돌린다.

### 6.4 이 비용의 성격

둘 다 **개발 머신에서 1회 실행**하는 빌드 타임 비용이다.

- 확장에 API 키가 들어가지 않는다
- `manifest.json`의 `host_permissions`는 그대로다
- 사용자는 여전히 정적 파일만 받는다. 런타임 비용은 0이다
- Firebase Blaze 전환이 필요 없다

선행 설계에서 LLM을 접은 이유는 **런타임** 비용이었다(클릭마다 호출). 지금은
성격이 다른 지출이다.

## 7. 데이터 스키마

기존 레코드에 **필드를 추가하지 않는다.** 생성된 대역어는 `ko`에 그대로 들어간다.

```js
{ pos: ["verb"], ko: ["참다","견디다","인내하다"], en: ["To tolerate; to endure"], ipa: "", mwe: true }
```

조회 계층(`lexicon/lookup.js`)과 팝업의 표시 로직은 `ko`가 채워졌는지만 보므로
그대로 동작한다.

다만 출처는 구분할 수 있어야 한다. 레코드에 `koSrc`를 둔다.

```js
koSrc: "wikt" | "gen"
```

`"gen"`인 항목은 팝업 하단 출처 표기를 "뜻: 기계 생성"으로 바꾼다. 위키 출처가
아닌 것을 CC BY-SA 표기 아래 두면 라이선스 표기가 거짓이 된다. 이건 런타임
변경이 필요한 유일한 지점이다.

## 8. 빌드 파이프라인 변경

**신규:** `tools/generate-lexicon.js`
- `dist/dict/`를 읽어 `ko`가 빈 표제어 중 범위(§4)에 드는 것을 추린다
- `lexicon/gloss-cache.json`에 이미 있는 항목은 건너뛴다
- 남은 것을 배치로 엔진에 보내고 결과를 캐시에 병합해 저장한다
- **멱등**이어야 한다. 중간에 죽어도 다시 실행하면 남은 것만 처리한다
- 진행률과 누적 비용을 출력한다

**수정:** `tools/build-dictionary.js`
- `buildBuckets`에서 레코드를 만들 때 `gloss-cache.json`을 조회해 `ko`가
  비어 있으면 채우고 `koSrc: "gen"`을 붙인다
- 위키 출처가 있으면 `koSrc: "wikt"`. **캐시가 위키를 덮지 않는다**

**수정:** `package.json` — `"gen:lexicon": "node tools/generate-lexicon.js"`

**순서:** `build:dict` → `gen:lexicon` → `build:dict` (2회차에 캐시가 주입된다).
1회차 빌드가 "무엇이 비었는지"를 알려주는 입력이 되므로 두 번 도는 게 자연스럽다.

## 9. 런타임 변경

거의 없다.

- `core/word-popup.js` — `koSrc === "gen"`이면 출처 표기 문구를 바꾼다 (§7)
- 그 외 `lexicon/*.js`, `background/service_worker.js`, `core/subtitle-engine.js`는
  변경 없음

버킷 크기는 늘어난다. 대역어가 붙는 106,418개 항목에 항목당 평균 30자 정도가
더해져 약 3MB 증가가 예상된다. 전체 165MB 대비 무시할 수준이고, 조회당 비용은
버킷 단위라 체감 변화가 없다.

## 10. 품질 검증

**생성물을 그대로 믿지 않는다.** 기계가 만든 대역어가 사전 행세를 하는 것이므로
검증이 이 작업의 핵심이다.

**1단계 — 표본 비교 (엔진 확정 전).** 양쪽 엔진으로 200개씩 생성해 나란히 놓고
사람이 본다. 표본은 무작위가 아니라 의도적으로 고른다:
- 흔한 구동사 50개 (`find out`, `deal with`, `put up with` …)
- 분리형 구동사 20개 (`look it up` 형태로 쓰이는 것)
- 연어 30개 (`heavy rain`, `make a decision` …)
- 다의어 50개 (`run`, `set`, `get` — 품사별로 갈리는 것)
- 빈도 상위 단어 50개

**Language Reactor의 답을 정답지로 쓴다.** 같은 표현을 LR API에 넣어 나온
대역어와 비교하면 사람이 판단하기 쉽다.

**2단계 — 자동 검사.** 생성 결과 전체에 대해:
- 한글이 하나도 없는 항목 (영어가 그대로 나온 경우)
- 표제어를 그대로 음차한 항목 ("풋 업 위드")
- 5개를 초과하는 항목, 빈 배열
- 대역어에 문장부호·따옴표·괄호가 섞인 항목

걸린 항목은 캐시에서 제외하고 영영 정의 폴백으로 남긴다.

**3단계 — 실기기 확인.** 선행 설계의 검증 절차를 따른다(재생 중 / 정지 상태
시점 이동 / 확장 재로드).

## 11. 리스크

| 리스크 | 대응 |
|---|---|
| 기계 대역어가 틀렸는데 사전처럼 보인다 | `koSrc`로 출처를 구분해 표기(§7). 자동 검사로 명백한 실패를 걸러냄(§10) |
| 문맥 없는 다의어의 엉뚱한 뜻 | 영영 정의를 함께 넘겨 완화. 근본 해결은 런타임 LLM이며 이번 범위 밖 |
| 비용이 추정보다 큼 | 배치를 나눠 실행하고 누적 비용을 출력. 1,000개 실행 후 실측으로 재추정 |
| 생성 중단 | 캐시가 멱등성을 보장(§8) |
| 라이선스 | 생성물은 위키 파생이 아니므로 CC BY-SA 표기 대상이 아니다. §7의 출처 구분이 이 문제도 함께 푼다 |

## 12. 미결

1. **엔진 선택.** §10 1단계 표본 비교 결과로 정한다.
2. **항목당 대역어 개수.** LR은 3~5개를 준다. 팝업 공간을 고려하면 4개가
   적당해 보이나 표본을 보고 정한다.
3. **품사 구분 유지 여부.** LR처럼 `posGroups`로 나눌지, 지금처럼 평면 배열로
   둘지. 평면이 기존 스키마와 호환되지만 `run`(동사/명사)처럼 갈리는 단어에서
   정보가 줄어든다.
